# Windows native resource core

The native-resource generator and its Task 31 build integration are code-ready.
Native compile/link, installed identity/icon/DPI and accessibility acceptance
remain open. The original icon source bytes remain authoritative and unchanged.
No Windows executable was compiled, linked, started, installed, signed or
published during implementation.

BUILD_INTEGRATION.md records the activated root build hook, explicit
product-windows-resources feature and maintained gpui-pre additive
windows-manifest-provided-by-host feature. Required identity/resource inputs are
checked before suppressing the dependency manifest. The native verifier enumerates
all manifest names/languages and refuses anything except resource ID 1 in English
(0x0409), then compares its exact bytes. The native driver supplies the generator's
inputs and requires that verifier on the exact resulting GUI.

The new inputs live in `packaging/native-resources/`. The new synthetic fixtures
live in `fixtures/native-resources/`; their version/build/source hash are not real
release metadata. Builds do not depend on ignored `docs/` or on a Mac asset build.
Python 3.11+ standard library and the existing packaging core are the only
generator dependencies. Native compilation later uses the existing supported
Visual Studio C++ Build Tools/Windows SDK and x64 MSVC toolchain.

## Prepared inputs and public API

`generate.py` imports the existing `packaging/package.py` and reuses its
`validate_identity`, `new_identity`, canonical JSON, source digest, safe input
handling and no-replace directory publication. It does not introduce a second
BuildIdentity schema or a new protocol/capability field. The public API is:

```python
render_resources(identity_data: bytes) -> dict[str, bytes]
```

The caller supplies the exact canonical `BUILD-IDENTITY.json` bytes, including
the final newline, generated by `package.py identity`. The API requires
`windows-x86_64-msvc`, `app.dbeer.DBeer`, the existing shared contract/capability,
and equality with the current source identity, `VERSION` and `BUILD_NUMBER`.
Stale/foreign metadata, unknown or duplicate fields, noncanonical JSON and input
over 4 KiB refuse. It returns:

| Input | Purpose |
| --- | --- |
| `dbeer.ico` | GUI icon group with integer resource ID 1 |
| `gui.manifest`, `gui.rc` | GUI execution/DPI settings and VERSIONINFO |
| `helper.manifest`, `helper.rc` | Optional helper VERSIONINFO/execution resources, with no UI/DPI declaration |
| `BUILD-IDENTITY.json` | Exact original canonical identity for input auditing |
| `NATIVE-RESOURCES.json` | Identity plus names, byte counts and SHA256 of generated inputs |

Resource ID 1 is used independently for ICON, VERSIONINFO and RT_MANIFEST;
resource types have separate namespaces. The helper template intentionally has
no application icon. Supplying its resource inputs does not wire Go embedding.
Both binaries still require the existing exact shared BuildIdentity embedding,
native `--build-info` handling and strict helper handshake from PACKAGING_CORE.
The JSON input is not added as RCDATA and cannot stand in for those runtime hooks.

`generate --identity <file> --output <new-directory>` writes the whole mapping.
`verify-inputs --identity <file> --inputs <directory>` compares all names and exact
bytes. `verify-native-pe` performs that same check, then inspects native PE
resources with Win32 data-resource and version APIs. Its required `--gui` and
optional `--helper` arguments never launch either executable. It checks PE32+
AMD64, the exact manifest bytes, all expected fixed/string version values, GUI
icon group 1 and every referenced icon image against the derived ICO.

All output directories must be new paths below the repository's ignored
`build/`. Existing directories, including empty ones, are never overwritten.
Inputs reject symbolic links/reparse points. Generation itself is portable static
asset preparation; it does not claim a native Windows build. Native PE inspection
additionally requires native Windows x64 and refuses cross-build overrides.
Native ACL and installed artifact acceptance remain pending.

## Exact version/build representation

Windows fixed FILEVERSION/PRODUCTVERSION and assembly versions have four
16-bit components. Their numeric tuple is exactly
`(VERSION.major, VERSION.minor, VERSION.patch, BUILD_NUMBER)`. Every component
must be 0 through 65535 inclusive; the shared build must also satisfy the existing
positive build-number contract. Overflow **refuses** before output is written.
There is no masking, modulo, truncation, clamping, Cargo version fallback or
release renumbering. A future shared version/build outside this representable
range requires an explicit project decision before a Windows candidate build.
[Microsoft documents the four WORD fields and their meaning](https://learn.microsoft.com/en-us/windows/win32/menurc/versioninfo-resource).

String `ProductVersion` is the exact shared VERSION, `BuildNumber` is the exact
shared BUILD_NUMBER, and `FileVersion` joins those exact strings with a period.
If a shared version has leading zeroes, the textual fields retain them while the
fixed binary and assembly fields necessarily represent the corresponding numeric
values. ProductName is DBeer; OriginalFilename is `dbeer-gpui.exe` or
`dbeer-core.exe`. ProductId and BuildTarget retain the authoritative identity.
VERSIONINFO marks these artifacts as development/prerelease. It does not claim
publisher authentication or replace the unsigned candidate policy.

## Unchanged icon derivation

The actual repository formats were inspected first: AppIcon.svg, the 1024px RGBA
AppIcon.png and AppIcon.icns already exist. ICNS contains smaller PNG renderings,
but the Windows derivation reads the chosen authoritative PNG directly, so the
Windows build does not consume Mac-only assets or depend on their regeneration.

The checked-in `dbeer.ico` is a format/size derivation of the existing artwork,
with no redesign, cropping, color substitution or added background. Ten sizes
are included: 16, 20, 24, 32, 40, 48, 64, 96, 128 and 256px. Its byte count is
419110 and SHA256 is
`5890c847962dbe602be3289f178d52e5f972417da7f130e6b72e76da53b269e4`.
`icon-provenance.json` binds the exact SVG, PNG and ICO SHA256 values and records
the sizes and resampling rule. The normal generator refuses stale provenance.

`derive-icon --output <new-build-directory>` reproduces ICO and provenance using
only Python integer arithmetic, zlib decompression and explicit PNG filters.
The decoder accepts the actual bounded noninterlaced 8-bit 1024px RGBA format and
validates CRCs and inflated size. Downsampling uses exact area overlap weights in
the source sRGB space and alpha-weighted color, preserving transparent-edge color.
No machine-specific image library, system image converter, resvg download or
network dependency is introduced. ICO frames use uncompressed 32-bit straight
alpha BGRA DIBs, bottom-to-top rows and DWORD-aligned AND masks. Uncompressed
frames keep output bytes independent of a compression library version. The
existing SVG/PNG originals and Mac icons are never written by the generator.
The [Windows icon resource format](https://learn.microsoft.com/en-us/windows/win32/menurc/resource-file-formats)
stores each frame as a resource referenced by an icon group.

To reproduce only the derived assets on any supported Python host:

```sh
python3.11 -B prototypes/gpui/packaging/native-resources/generate.py derive-icon \
  --output build/gpui/native-icon-review
```

Compare the resulting ICO and provenance to the checked-in pair before any
future deliberate icon update. Do not copy generated files over existing source
assets automatically. Explorer/taskbar visuals at every scale still require
native review in light and dark desktop themes.

## Pinned GPUI requirements and the manifest collision

Actual locked source was inspected, including these crate archive checksums:

| Package | Locked checksum |
| --- | --- |
| `gpui-kit` 0.7.3 | `0fac401f6b149bf33794da0942510240afd29b7b18556574e4cf17196b647066` |
| `gpui-pre` 0.3.9 | `34f61c1cfd36fc9c436af09308c963822ae27a45a84feb21a77ba5c9e051f1c0` |
| `gpui-pre-windows` 0.3.9 | `513d4f0fc7d596d3bdef2a73a524ffb83dabc95bf484f2855a698e7f431290a9` |

Primary source archives are on crates.io:
[gpui-kit](https://static.crates.io/crates/gpui-kit/gpui-kit-0.7.3.crate),
[gpui-pre](https://static.crates.io/crates/gpui-pre/gpui-pre-0.3.9.crate),
[Windows backend](https://static.crates.io/crates/gpui-pre-windows/gpui-pre-windows-0.3.9.crate).
No downloaded source is required at build time beyond the existing locked crates.

- `gpui-pre-windows/src/platform.rs::load_icon` calls `LoadImageW` on the host
  module using integer resource ID 1, IMAGE_ICON, LR_DEFAULTSIZE | LR_SHARED.
  `window.rs::register_window_class` sets that HICON on WNDCLASSW. An ICO merely
  shipped beside the binary cannot satisfy this path. The new GUI RC uses ID 1.
- `window.rs` reads GetDpiForWindow; `events.rs` handles WM_DPICHANGED, updates
  scale_factor/direct manipulation and applies the supplied rectangle or the
  maximized monitor work area. This source behavior informed the declaration;
  it does not establish correct behavior for the complete DBeer interface.
- `gpui-pre/resources/windows/gpui.manifest.xml` declares `true/pm`,
  `PerMonitorV2`, SegmentHeap and Common-Controls v6. The host GUI manifest keeps
  these settings rather than replacing them with a generic system-DPI manifest.
  It adds the product assembly identity, exact four-part version and amd64 CPU.
- `gpui-pre` default features include **windows-manifest**. Its build.rs invokes
  embed-resource on `resources/windows/gpui.rc`, which embeds RT_MANIFEST **1**.
  The current gpui-kit and vendored gpui-base both depend on gpui-pre with its
  defaults. The separate optional gpui-fast feature
  `windows-manifest-provided-by-host` does not disable gpui-pre's default feature.

The integrated maintained gpui-pre feature resolves this collision: an explicit
host-manifest feature suppresses its embed-resource branch after validating the
native release identity and generated resources, while ordinary defaults retain
the upstream manifest. Cargo features unify additively; disabling one
dependency edge alone does not prove the feature absent. Inspect native
`cargo tree -e features -i gpui-pre` and the linker inputs after the change.
`/MANIFEST:NO` controls linker manifest generation; it does **not** remove an
RT_MANIFEST already embedded by a dependency. Do not link two resource 1 manifests
and assume which one Windows will use. The paired driver records the actual
feature graph and verifies exactly one native manifest in the resulting PE.

The compatibility GUID `{8e0f7a12-bfb3-4fe8-b9a5-48fd50a15a9a}` is Microsoft's
documented shared Windows 10/11 GUID. It does not expand the supported product
matrix beyond Windows 11 x64 or enforce a minimum Windows build by itself.
No `maxversiontested` claim is made. Both manifests use
`requestedExecutionLevel=asInvoker` and `uiAccess=false`; no elevation, signing,
trust change or accessibility privilege is requested.
[Microsoft's manifest reference](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests)
defines these declarations. PerMonitorV2 is the pinned backend's intended mode;
[Microsoft's DPI guidance](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)
does not make the manifest a proof of correct fractional or mixed-monitor layout.

## Required later native compile/link/verification

The commands below are low-level historical handoff examples, **not executed
here**. The supported integrated wrappers in BUILD_INTEGRATION.md supply these
inputs automatically. Run only after
the remaining implementation through Task 32 is integrated, with the actual
source frozen. Use native Windows 11 x64 Developer PowerShell, Python 3.11+,
x86_64-pc-windows-msvc Rust, the existing Windows SDK and C++ tools. Choose new
owned build directories; no example grants permission to overwrite an archive.

```powershell
$repoRoot = (Get-Location).Path
$identity = Join-Path $repoRoot 'build/gpui/product-identity.json'
$resourceTool = Join-Path $repoRoot 'prototypes/gpui/packaging/native-resources/generate.py'
$inputs = Join-Path $repoRoot 'build/gpui/native-resources-inputs'
$compiled = Join-Path $repoRoot 'build/gpui/native-resources-compiled'
$guiRes = Join-Path $compiled 'gui.res'
$helperRes = Join-Path $compiled 'helper.res'
$env:CARGO_TARGET_DIR = Join-Path $repoRoot 'build/gpui/target'

# Existing identity command refuses non-native Windows/x64/cross-build overrides.
py -3 prototypes/gpui/packaging/package.py identity --target windows-x86_64-msvc --output $identity
if ($LASTEXITCODE -ne 0) { throw 'Identity generation failed.' }
py -3 -B $resourceTool generate --identity $identity --output $inputs
if ($LASTEXITCODE -ne 0) { throw 'Resource generation failed.' }
New-Item -ItemType Directory -Path $compiled -ErrorAction Stop | Out-Null
Push-Location $inputs
try {
    rc.exe /nologo /c65001 /fo $guiRes gui.rc
    if ($LASTEXITCODE -ne 0) { throw 'GUI RC compilation failed.' }
    rc.exe /nologo /c65001 /fo $helperRes helper.rc
    if ($LASTEXITCODE -ne 0) { throw 'Helper RC compilation failed.' }
} finally {
    Pop-Location
}

# Only AFTER the duplicate GPUI manifest has been resolved and both metadata
# build hooks are integrated. Do not rebuild an unmarked helper afterward.
$env:DBEER_PRODUCT_BUILD_IDENTITY = (Get-Content -Raw $identity).TrimEnd([char[]]"`r`n")
cargo rustc --locked --release --manifest-path prototypes/gpui/Cargo.toml --bin dbeer-gpui -- `
  -C "link-arg=$guiRes" -C link-arg=/MANIFEST:NO
if ($LASTEXITCODE -ne 0) { throw 'Native GUI link failed.' }
```

This explicit cargo rustc command demonstrates the native MSVC link input.
The production build hook should compile the RC from its input directory and
pass only the GUI `.res` to `cargo:rustc-link-arg-bin=dbeer-gpui`, with rerun
tracking for the identity, templates, ICO, VERSION/BUILD_NUMBER and relevant
environment. It must guard the actual native release target and preserve ordinary
Mac/Linux/dev builds. No process-global RUSTFLAGS should inject GUI resources
into dependencies, tests or the helper. The existing root build scripts must not
silently rebuild a helper without the same canonical metadata afterward.
[Microsoft describes RC compilation](https://learn.microsoft.com/en-us/windows/win32/menurc/using-rc-the-rc-command-line-)
and [linking the resulting .res](https://learn.microsoft.com/en-us/windows/win32/menurc/about-resource-files).
The [linker manifest option](https://learn.microsoft.com/en-us/cpp/build/reference/manifest-create-side-by-side-assembly-manifest)
must be chosen consistently with the sole embedded host manifest.

The optional helper RC is prepared, but a Go resource hook is not. A later
integrator who chooses helper VERSIONINFO must validate an x64 COFF resource
object with the exact Go toolchain and place it only in a dedicated product build
workspace under ignored build/, preserving ordinary helper/Mac builds. Do not
add a generated `.syso` to tracked helper sources or claim MSVC link input alone
proves Go resource support. The existing helper BuildIdentity/handshake contract
remains mandatory regardless of whether this optional native helper resource is
used. Do not pass `--helper` below until its generated resources are linked.

After linking, inspect the exact candidate binary without starting it:

```powershell
$gui = Join-Path $env:CARGO_TARGET_DIR 'release/dbeer-gpui.exe'
dumpbin.exe /HEADERS $gui
if ($LASTEXITCODE -ne 0) { throw 'PE inspection failed.' }
mt.exe -nologo "-inputresource:$gui;#1" "-out:$compiled/gui.extracted.manifest"
if ($LASTEXITCODE -ne 0) { throw 'Manifest extraction failed.' }
mt.exe -nologo -manifest (Join-Path $inputs 'gui.manifest') -validate_manifest
if ($LASTEXITCODE -ne 0) { throw 'Manifest validation failed.' }
py -3 -B $resourceTool verify-native-pe --identity $identity --inputs $inputs --gui $gui
if ($LASTEXITCODE -ne 0) { throw 'Native resources do not match the frozen inputs.' }
# If the helper resource hook is implemented, add --helper <exact dbeer-core.exe>.
```

The generator's Win32 verifier maps PE resources using
[LoadLibraryExW data/image-resource flags](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-loadlibraryexw)
and reads fixed/string versions with
[GetFileVersionInfoW](https://learn.microsoft.com/en-us/windows/win32/api/winver/nf-winver-getfileversioninfow)
and [VerQueryValueW](https://learn.microsoft.com/en-us/windows/win32/api/winver/nf-winver-verqueryvaluew).
This establishes resource bytes when completed successfully, not GPU rendering,
desktop identity, window/taskbar behavior, DPI correctness or installed acceptance.
The external [mt.exe inspection](https://learn.microsoft.com/en-us/windows/win32/sbscs/mt-exe)
is retained as an independent SDK check. Full candidate packaging still requires
the hardened packager's GUI/helper BuildIdentity/embedded marker/build-info,
native dependency, notices and checksum checks from PACKAGING_CORE.

canonical bytes, wrong target, numeric version boundaries, both version string

```sh
python3.11 -B -m unittest discover \
  -s prototypes/gpui/packaging/native-resources -p test_native_resources.py -v
```

No prepared unit/native test has executed under the user's deferred-test policy.
The macOS preparation host had no rc.exe, llvm-rc or PowerShell available. The
default python3 was below the required Python version; asset derivation used the
already installed Python 3.14. On 2026-10-20, static icon derivation, source-bound
hashes, ICO offsets/frame/DIB sizes, Python AST syntax, fixture JSON, rendered

completed. Static inputs for the then-current VERSION 0.1.0 / BUILD_NUMBER 6 were

SVG/PNG/ICNS have no git diff, the output path is ignored, and the owned text
